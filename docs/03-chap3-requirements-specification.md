# Capítulo III: Requirements Specification

## 3.1. To-Be Scenario Mapping

*Qué debe ir: Presentar un To-Be Scenario Map por cada User Persona, con Phases, Doing, Thinking y Feeling. Explicar el proceso y compararlo con el As-Is Scenario Mapping para identificar los cambios que plantea el escenario futuro.*

## 3.2. User Stories.

*Qué debe ir: Redactar una introducción y un único cuadro para Epics/User Stories con ID, título, descripción, criterios de aceptación y Epic relacionado. Los criterios deben ser comprobables, en presente y tercera persona, sin detalles de UI, y seguir Gherkin (Given-When-Then) salvo reglas/restricciones aplicables. Considerar stories de Landing Page y Technical Stories para funcionalidades sin interacción directa, como RESTful APIs.*

## 3.3. Impact Mapping

*Qué debe ir: Explicar y presentar el Impact Map. Definir varios Business Goals SMART; relacionar Actors/Personas con los User Persona; indicar los cambios de comportamiento esperados en Impact; los Deliverables que puede producir el negocio; y las User Stories que soportan dichos deliverables.*

## 3.4. Product Backlog

*Qué debe ir: Incluir priorización y estimación de User Stories. Presentar una tabla con orden, User Story ID, título, descripción y Story Points (1/2/3/5/8), además de screenshot y URL pública del backlog en la herramienta indicada. El orden debe responder al valor para el negocio y las stories del Landing Page deben considerarse desde el primer sprint.*
