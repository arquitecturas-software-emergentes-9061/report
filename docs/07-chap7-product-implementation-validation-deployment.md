# Capítulo VII: Product Implementation, Validation & Deployment

## 7.1. Software Configuration Management

*Qué debe ir: Definir decisiones y convenciones para mantener consistencia durante el ciclo de vida, incluyendo configuración del entorno, gestión de código fuente, guía de estilo/coding y configuración de despliegue.*

### 7.1.1. Software Development Environment Configuration

*Qué debe ir: Especificar los productos de software utilizados, su propósito y la ruta de referencia/descarga, cubriendo actividades como Project Management, Requirements Management, Product Design, Development, Testing, Deployment y Documentation, respetando las herramientas permitidas.*

### 7.1.2. Source Code Management

*Qué debe ir: Indicar la URL de GitHub para cada producto digital. Explicar GitFlow, branches y convenciones para feature/release/hotfix, aplicar Semantic Versioning para releases y Conventional Commits para mensajes de commit. En Web Services, incluir también archivos de pruebas como .feature cuando corresponda.*

### 7.1.3. Source Code Style Guide & Conventions

*Qué debe ir: Resumir e indicar las referencias de estilo y convenciones para cada lenguaje utilizado (incluido Gherkin cuando corresponda). La nomenclatura debe estar en inglés y deben adoptarse convenciones estándar de coding.*

### 7.1.4. Software Deployment Configuration

*Qué debe ir: Especificar la configuración y los pasos necesarios para desplegar/publicar cada producto digital a partir de sus repositorios. Incluir también el Deployment Diagram de C4 Model.*

## 7.2. Solution Implementation

*Qué debe ir: Explicar y evidenciar implementación, pruebas, documentación y despliegue de los productos digitales. La estructura final contempla el avance por Sprints.*

### 7.2.1. Sprint 1

*Qué debe ir: Registrar y explicar el avance del Sprint 1 en términos de producto y trabajo colaborativo. Incluir Planning, Backlog, evidencias de desarrollo, testing, ejecución, documentación de servicios, despliegue y colaboración.*

#### 7.2.1.1. Sprint Planning 1

*Qué debe ir: Introducir el Sprint Planning Meeting y completar el cuadro indicado: Sprint, fecha, hora, ubicación, preparado por, asistentes, resumen del review y retrospectiva anterior (cuando aplique), Sprint Goal, métrica de cumplimiento, Velocity y suma de Story Points.*

#### 7.2.1.2. Sprint Backlog 1

*Qué debe ir: Incluir una introducción con el objetivo del Sprint, screenshot y URL pública del Board. Añadir una tabla con User Stories y Work-items/Tasks, incluyendo ID, título, descripción, estimación en horas, responsable y estado (To-do/In-Process/To-Review/Done).*

#### 7.2.1.3. Development Evidence for Sprint Review

*Qué debe ir: Resumir los avances de implementación y presentar una tabla de commits por repositorio con Repository, Branch, Commit Id, Commit Message, Commit Message Body y fecha de commit.*

#### 7.2.1.4. Testing Suite Evidence for Sprint Review

*Qué debe ir: Explicar y presentar Unit Tests, Integration Tests y Acceptance Tests automatizados relacionados con las User Stories del Sprint. En BDD, incluir .feature en Gherkin y Steps; relacionar pruebas con clases o stories e incluir repositorios y commits de testing.*

#### 7.2.1.5. Execution Evidence for Sprint Review

*Qué debe ir: Iniciar con un resumen de lo alcanzado en el Sprint, mostrar screenshots de las principales vistas implementadas e incluir un enlace a un video que demuestre y explique la visualización y navegación logradas.*

#### 7.2.1.6. Services Documentation Evidence for Sprint Review

*Qué debe ir: Documentar los endpoints del Sprint mediante OpenAPI. Incluir acciones soportadas, verbo HTTP, sintaxis, parámetros, ejemplos y explicación del response; añadir capturas con datos de muestra, URL del repositorio y commits relacionados con la documentación.*

#### 7.2.1.7. Software Deployment Evidence for Sprint Review

*Qué debe ir: Resumir las actividades de Deployment realizadas durante el Sprint: cuentas, recursos cloud, integración o automatización de despliegue y demás pasos aplicables a los productos digitales. Añadir capturas y explicaciones.*

#### 7.2.1.8. Team Collaboration Insights during Sprint

*Qué debe ir: Explicar cómo se desarrollaron las actividades de implementación e incluir analíticos de colaboración y commits de GitHub. Todos los integrantes deben evidenciar participación en la implementación de los productos que corresponden al Sprint.*

## 7.3. Validation Interviews

*Qué debe ir: Registrar y explicar las entrevistas de validación en las que usuarios de los segmentos objetivo interactúan con el Landing Page y las aplicaciones. La sección incluye diseño, registro y evaluación heurística.*

### 7.3.1. Diseño de Entrevistas

*Qué debe ir: Definir, por segmento objetivo, los elementos de la sesión de validación, incluyendo Landing Page y aplicaciones, e indicar los User Flows que se evaluarán.*

### 7.3.2. Registro de Entrevistas

*Qué debe ir: Realizar de 3 a 5 entrevistas por segmento. Registrar nombres, apellidos, edad, distrito, screenshot, URL en Microsoft Stream, timing y duración, y redactar un resumen descriptivo de las apreciaciones del entrevistado respecto a las tareas asignadas.*

### 7.3.3. Evaluaciones según heurísticas

*Qué debe ir: Aplicar el formato del Anexo D para evaluar la experiencia según heurísticas de usabilidad, arquitectura de información e inclusive design. Registrar problemas, severidad, heurística/principio afectado, evidencia y recomendación según el formato.*

## 7.4. Video About-the-Product

*Qué debe ir: Introducir y describir el video orientado a visitantes y usuarios. Debe resumir modelo de negocio, características y beneficios, incluir escenas de interacción y al menos un testimonio positivo por segmento. Incluir screenshot, URL en Microsoft Stream, URL en YouTube y timing; además se incrusta en el Landing Page. El Anexo C indica una duración de 1 a 3 minutos.*
